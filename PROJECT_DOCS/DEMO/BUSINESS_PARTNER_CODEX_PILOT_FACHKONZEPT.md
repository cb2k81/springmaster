# Business Partner Codex Pilot Fachkonzept

## 1. Purpose

This dummy domain concept is the immutable V1 business input for the Springmaster Codex pilot. It is intentionally realistic enough to exercise list, detail, create, edit, command, reference-data and relationship patterns without external integrations, file uploads, asynchronous processing or production deployment.

It is not a real customer or master-data specification. Names and examples are synthetic.

## 2. Business objective

Administrative users manage business partners used as selectable organizational counterparts. A business partner has a stable business code, descriptive data, a type, a lifecycle status and zero or more contact methods.

The generated application must support controlled maintenance and reliable selection while keeping inactive partners visible for history and excluding them from active-only selectors.

## 3. Terms

| Term | Meaning |
|---|---|
| Business Partner | An organization or person represented as an administrative counterpart. |
| Partner Type | Controlled reference value `ORGANIZATION` or `PERSON`. |
| Active Partner | A partner permitted for new selections and normal operations. |
| Inactive Partner | A retained partner not permitted for new active-only selections. |
| Contact Method | A child record containing one communication channel. |

## 4. Aggregate and identity requirements

- **BP-REQ-001:** The aggregate root is `BusinessPartner`.
- **BP-REQ-002:** The public technical identifier is an opaque string generated by the backend and never entered by the user.
- **BP-REQ-003:** `code` is the stable human-readable business key and is unique case-insensitively after trimming.
- **BP-REQ-004:** Changing `code` after creation is not allowed in V1.
- **BP-REQ-005:** A partner contains zero or more `ContactMethod` child records. Child records have opaque identifiers internal to the aggregate boundary.

## 5. Business Partner data

| Field | Type | Rules |
|---|---|---|
| `id` | opaque string | backend-generated, read-only |
| `code` | string | required on create, trimmed, 2–32 characters, uppercase letters, digits and hyphen, immutable, unique |
| `name` | string | required, trimmed, 1–255 characters |
| `description` | string | optional, trimmed, maximum 1000 characters |
| `partnerType` | reference enum | required; `ORGANIZATION` or `PERSON` |
| `status` | lifecycle enum | backend-managed; initial value `ACTIVE`; values `ACTIVE`, `INACTIVE` |
| `version` | opaque concurrency value | backend-managed, used to detect conflicting updates |

- **BP-REQ-010:** Create requires `code`, `name` and `partnerType`.
- **BP-REQ-011:** Update requires `name` and `partnerType`; `code`, `id`, `status` and `version` are not freely editable.
- **BP-REQ-012:** Validation errors identify the affected field and use the global API error contract.
- **BP-REQ-013:** A duplicate normalized `code` is a conflict and must not create or overwrite a partner.
- **BP-REQ-014:** A stale `version` update is a conflict and must not overwrite newer data.

## 6. Contact methods

A contact method belongs to exactly one business partner.

| Field | Type | Rules |
|---|---|---|
| `id` | opaque string | backend-generated |
| `kind` | enum | required; `EMAIL`, `PHONE`, `WEB` |
| `value` | string | required, trimmed, maximum 255 characters |
| `label` | string | optional, trimmed, maximum 80 characters |
| `primary` | boolean | required, default `false` |

- **BP-REQ-020:** At most one contact method may be primary per partner.
- **BP-REQ-021:** An email value must use a syntactically valid email address.
- **BP-REQ-022:** A web value must be an absolute HTTP or HTTPS URL.
- **BP-REQ-023:** A phone value is stored as entered after trimming; V1 does not implement country-specific normalization.
- **BP-REQ-024:** Contact methods are maintained inside the partner create/edit flow and are persisted atomically with the aggregate.

## 7. Lifecycle commands

- **BP-REQ-030:** A newly created partner is `ACTIVE`.
- **BP-REQ-031:** `deactivate` changes `ACTIVE` to `INACTIVE`.
- **BP-REQ-032:** `activate` changes `INACTIVE` to `ACTIVE`.
- **BP-REQ-033:** Repeating the command for the current state is rejected as an invalid command state and does not modify data.
- **BP-REQ-034:** Deactivation does not delete the partner or its contact methods.
- **BP-REQ-035:** Hard delete is allowed only for a partner that has never been referenced by another aggregate. The pilot may use a deterministic reference-check stub, but the contract must make the condition explicit.

## 8. Query requirements

### 8.1 List

- **BP-REQ-040:** The list is paged and supports `page`, `size`, `sortBy` and `sortDir`.
- **BP-REQ-041:** Allowed sort fields are `code`, `name`, `partnerType` and `status`, with a stable technical tie-breaker.
- **BP-REQ-042:** Filters support code contains, name contains, exact partner type and exact status.
- **BP-REQ-043:** Default sorting is `code asc`.
- **BP-REQ-044:** Each row shows code, name, partner type, status and primary contact summary.

### 8.2 Detail and lookup

- **BP-REQ-045:** Detail lookup by opaque `id` returns all aggregate data and contact methods.
- **BP-REQ-046:** Alternate lookup by exact normalized `code` returns one partner or not found.
- **BP-REQ-047:** Unknown identifiers and codes return the global not-found error.

### 8.3 Options

- **BP-REQ-048:** An options endpoint returns active partners only, sorted by code, with opaque ID and display label `code – name`.
- **BP-REQ-049:** The options endpoint is bounded by a required search term or an explicit maximum result limit documented in the generated specification.

## 9. Roles and permissions

The application checks permissions, not role names.

| Permission | Purpose |
|---|---|
| `administration:business-partner:read` | list, detail, lookup and options |
| `administration:business-partner:create` | create |
| `administration:business-partner:update` | edit descriptive data and contact methods |
| `administration:business-partner:activate` | activate |
| `administration:business-partner:deactivate` | deactivate |
| `administration:business-partner:delete` | conditional hard delete |

- **BP-REQ-050:** Every operation is classified as management and requires its operation permission.
- **BP-REQ-051:** An unauthenticated request returns `401`; an authenticated request without permission returns `403`.
- **BP-REQ-052:** UI capability information may hide or disable actions but never replaces backend authorization.

## 10. UI requirements

### 10.1 Navigation and list

- **BP-REQ-060:** The app exposes a navigation item “Business Partners” for users with read permission.
- **BP-REQ-061:** The list page provides filters for code/name text, partner type and status.
- **BP-REQ-062:** Filter and sort state are representable in the URL so the view can be reopened.
- **BP-REQ-063:** The page defines loading, empty, error and forbidden states.
- **BP-REQ-064:** Create is visible only with create capability.

### 10.2 Detail

- **BP-REQ-065:** Detail shows identity, descriptive data, lifecycle status and contact methods.
- **BP-REQ-066:** Edit, activate, deactivate and delete actions reflect capability and current lifecycle state.
- **BP-REQ-067:** A failed command leaves the displayed state unchanged and presents the global error identity.

### 10.3 Create and edit

- **BP-REQ-068:** Create and edit use explicit forms with field-level errors and a summary for non-field errors.
- **BP-REQ-069:** Contact methods can be added, edited, removed and marked primary in the same form.
- **BP-REQ-070:** Unsaved-change protection is required when leaving a changed form.
- **BP-REQ-071:** Successful create navigates to detail; successful edit refreshes the detail state.
- **BP-REQ-072:** On optimistic conflict, the user is told that newer data exists and no silent overwrite occurs.

## 11. Accessibility and localization

- **BP-REQ-080:** All form controls have programmatic labels and errors are associated with their controls.
- **BP-REQ-081:** Status and validation meaning are not communicated by color alone.
- **BP-REQ-082:** Keyboard access covers filters, table actions, forms and dialogs.
- **BP-REQ-083:** User-facing strings are externalized for localization; the pilot acceptance language is English.

## 12. Explicit non-goals

V1 does not include:

- external CRM, ERP, email or telephony integration;
- file upload, logos or attachments;
- asynchronous workflows or multi-stage approval;
- merge/duplicate resolution;
- address validation or geocoding;
- production deployment or migration of a real business-partner dataset;
- mutation of GWC, Personnel or any managed project.

## 13. Required transformation chain

The pilot must produce separate reviewable artifacts:

1. canonical domain intent with every requirement ID;
2. generated-slice specification;
3. neutral intermediate representation;
4. Application UI Spec;
5. GWC implementation manifest;
6. generated disposable GWC application;
7. traceability and acceptance evidence.

No stage may silently invent a field, command, permission or relationship. Ambiguity is emitted as a blocking finding.

## 14. Version and freeze

This document is pilot input version `1.0.0` and is frozen for the first generation run. A later V1.1 evolution task will add one controlled requirement change without rewriting V1 history.
